## Context

A public repository alone does not grant an open-source license or establish sustainable maintenance; no license choice is assumed.

Direction: [open-source scope and future decisions](../future-scope.md).
Baseline: [2026-10-04](../baseline.md). Preserve existing implementations and safety gates.
Discussion/selection tasks are not proof of implementation or permission for cloud changes.

## Acceptance Criteria

- [ ] Obtain maintainer approval for a code license and add LICENSE, notices and package metadata; distinguish code licensing from source-data rights.
- [ ] Publish contribution, conduct, governance and private vulnerability-reporting policies; identify maintainer and review responsibilities without inventing contacts or response promises.
- [ ] Define release versioning, support/deprecation policy, changelog and dependency update ownership; track SBOM/dependency/license checks with TS-029.
- [ ] Provide rights-safe examples and a documented first-contribution path; never redistribute raw personal data or licensed source datasets by default.

## Verification

Check license/metadata consistency, documentation links, contributor clean-checkout workflow and dependency/data redistribution review.

Record commands/results, decisions, deferred child issues and live versus fixture/replay boundaries.

## Guardrails

- No secrets, raw personal data, synthetic live fallbacks or source-rights bypasses.
- Cloud/account/schedule changes and paid access require explicit approval.
- Preserve provenance, pending/blocked coverage and trusted tenant/actor boundaries.
- No unsupported legal verdicts or scores from incomplete identity/evidence/coverage.
